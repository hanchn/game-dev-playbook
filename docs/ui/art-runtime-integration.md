# 游戏美术到运行时：身份、槽位、加载与公共反馈

这份方法来自《恐龙消防员》中被用户明确拒收的实际画面，以及随后接入的原图、标定数据和运行时代码。它解决的是“有设计稿、有 PNG，但游戏里仍然不像、错位、闪入、被裁切”的问题。复用生产与诊断方法，不照搬这个游戏的尺寸、按键位置或颜色阈值。

**证据状态：**规则回归曾记录为 31/31 通过，这是已有基线，本次文档整理没有重新执行测试；已有浏览器记录观察到开始后加载、跑动恐龙、独立夜间素材和 60 FPS 快照。所有最新状态尚未完成原生浏览器美术复核，用户未接受的资产仍为 `pending`，不能写成“已验收”。

## 1. 先锁定角色身份，再复用动作支持库

“已有恐龙技能库，只换卡通皮肤”不等于可以保留一具不匹配的瘦长骨架，再零散粘贴头、帽子、靴子。用户确认的是胖胖、可爱、厚实四肢的消防员；若运行时仍是细腿、歪嘴，即使都叫恐龙，也没有满足身份要求。

建立一张角色身份基准，包含头身比、脸和嘴型、眼睛位置、腹部体积、大腿与小腿粗细、尾巴比例、服装材质、朝向，以及持物方式。保存用户确认的主视觉原始文件，后续每组动作并排比较，不以“同一提示词”或“同一颜色”证明一致。

| 失败表现 | 原因定位 | 修复方法 | 可证明的结果 |
|---|---|---|---|
| 首页角色圆胖，局内角色瘦长、嘴歪 | 换头和服装不能改变旧骨架的形体；局部变换使脸部受损 | 以批准形象生成完整动作序列，重新标定；能力库继续提供状态和交互逻辑 | 同屏展示首页、站立、跑动、取水、倒水的固定比例对照，再播放 |
| 帽子像漂浮零件、靴子脱离腿 | 已烘焙服饰与运行时叠件混用，或部件锚点错误 | 每个动作明确服饰归属：完整角色帧内已有的帽子、背心、靴子不再另叠一遍 | 最极端姿势和切换瞬间没有双帽、双靴或断肢 |
| 西装只剩一个前视胸口，鳄鱼身体不完整 | 服装视角、身体视角和裁切规则不一致 | 先形成完整侧身形象，再设计水面遮挡与攻击帧 | 离水完整角色、潜水角色、攻击角色分别检查，区分素材缺失和遮挡错误 |
| 动画动作正确但上下抽动、忽大忽小 | 逐帧按可见包围盒缩放或忽略透明边 | 固定画布和稳定形体尺度；接地校正只补垂直偏移，不逐帧缩放 | 头宽、躯干和髋部尺度稳定；脚在预定支撑阶段接地 |

能力库可复用状态机、输入、事件、冷却和骨骼解算；美术身份、肢体比例与每个动作的物理语义需要单独验收。新序列若已画出倒水水流，运行时应移除旧喷射曲线；两套水流同时存在，是重复表现，不是效果更丰富。取水需看见俯身、桶口入水、提桶；倒水需看见桶口向外下倾，不能仅旋转到面前而像喝水。

## 2. 每种 UI 都有专用原图和内容区

先列出完整屏幕与组件：入口主视觉、标题、开始按钮、加载轨道、HUD、方向键、动作键、火势牌、取水提示、公共消息、暂停和结算。给每项明确用途、图层、动态信息和状态。不要只画一块通用木框，然后把所有页面都塞进去。

原创 PNG 负责材质、边角、光向与装饰；数字、可变文字、图标、交互区和状态负责运行时表达。标题字图可独立作为主题资产，但按钮文字、比分、容量和消息不应焊死在整屏背景里。首页是一个完整构图，需要统一角色、留白、主按钮和文字层级，不能用一张背景加几个默认文本当作完成。

每个组件至少记录：

```json
{
  "sourceSize": [1881, 836],
  "contentBounds": {"meaning": "在原图像素坐标中标定，示例不提供通用数值"},
  "alphaSafety": {"include": ["轮廓", "投影", "光晕"]},
  "slots": ["icon", "value", "fill"],
  "scaleMode": "uniform",
  "states": ["normal", "pressed", "disabled"],
  "userAcceptance": "pending"
}
```

内容边界、透明安全边、热区是三个不同概念。完整 PNG 画布可能有很大透明边；把标签放在整张图的几何中心，不等于放进可见槽位中心。先看真实原图和透明通道，再标定文字安全区；用长文本、零值、最大值与低分辨率检查边框、高光是否挤压关键内容。

旧结算图下方带了一块未使用的空白按钮位，用户看到了“多出来一个按钮”。正确修复是重新出适配双按钮的干净面板，并验证整个轮廓；不能继续叠按钮、用背景色遮盖，或把空槽当作无关装饰。火势标签也应设计为明确的状态组件，不能因为主按钮精细，就容忍局部仍使用随手画的椭圆和细线。

## 3. 原图设计坐标是 HUD 标定依据

本例 `hud-v2.png` 为 **1881×836**，在 1100×570 逻辑画布中以 `(168,48)` 为图像中心、宽 310 等比绘制。原图点到逻辑点的关系为：

```text
s = displayWidth / sourceWidth
screenX = imageCenterX + (sourceX − sourceWidth / 2) × s
screenY = imageCenterY + (sourceY − sourceHeight / 2) × s
```

原图水槽中部约位于源像素 `y=400.5`，换算后中心约 `y=45.2`，并不是整张图像中心 `y=48`。此前水条按主观位置画在槽底、文字又单独放置，导致“进度条没贴合”。接入版本改用填充起点 `(88,37)`、总宽 140、高 16，容量文字中心 `(270,45)`；这些是**这一版原图的实例参数**，换图后必须重新测量，不应复制成默认规范。

水条至少用 0%、少量、60%、100% 检查。全量时不能盖住金属边框，少量时圆角不能比实际填充更宽，空量时不能残留一块高光。文字显示值、条形比例和真实水量必须来自同一个模型值；数值布局不能用空格凑齐。

## 4. 弯曲进度轨道要有相同形状的填充遮罩

`load-track-v3.png` 是 **2079×756** 的起伏轨道。最初使用一个 `left:12%; top:42%; height:8%` 的直矩形填充；它只能贴住局部，在弧线处必然穿框或留空。给矩形加圆角不能修复形状不一致。

优先让美术同时提供独立槽位遮罩或明确的闭合轮廓。当前接入使用受限的连通区域扫描，保留原始轨道字节，只由运行时绘制动态填充：

1. 等轨道图片 `decode()` 成功，用原始像素尺寸建立离屏画布。
2. 限制扫描范围在预先量出的中央槽位区域，避免叶片、徽章、投影被误认为槽。
3. 从槽内已验证的种子出发，用颜色与透明度条件找四邻域连通区域。
4. 生成 alpha 遮罩；先画遮罩，再用 `source-in` 合成渐变和真实进度宽度。
5. 保留木头、石块、金属和原画外轮廓，不对整张 PNG 做拉伸或覆盖。

本例种子为 `(0.5w,0.57h)`；区域约束为 `0.12w<x<0.88w`、`0.28h<y<0.67h`，并要求 alpha 大于 200 及特定深绿色条件。这些阈值仅对当前图片成立。离线检查得到 **135973 个连通像素**、范围 `x262…1810 / y309…481`、**1549 个连续列**。这证明遮罩找到了连续槽区，不能替代实际显示的边缘观感检查。

| 失败模式 | 需要识别的证据 | 生产处理 |
|---|---|---|
| 换图后种子落在石框上 | 连通面积为零、列跨度不足 | 标定种子或使用独立遮罩；不能继续显示空进度条却宣称加载正常 |
| 深绿色叶片与槽相连 | 遮罩面积异常，连通边界越过中央区域 | 收紧区域并检查左右端点；不要盲目放宽颜色阈值 |
| 反光把槽分成多段 | 连续列覆盖出现缺口 | 优先使用美术输出的专用遮罩；种子和颜色方法不是通用分割模型 |
| 半透明像素导致破边或漏扫 | 查看 alpha、边缘放大图及不同底色 | 保留安全边，标明源图透明策略，重新检查阈值 |
| 扫描失败却悄悄退回普通直条 | 视觉又出现两套不一致轨道 | 保持唯一轨道，显示明确失败或静态准备状态；修复后再启用动态填充 |

当前代码已经实现受限扫描和连通遮罩，但**没有完整的自动面积/覆盖率拒绝门槛**；上表中的质量门槛是后续复用时应增加的保护，不要误写为已经上线的能力。

## 5. 加载跑动角色：动作帧与进度位移分开

本例跑动序列为 2×2 网格，每格 627×627，CSS 固定显示 128×128；每 100 ms 换一帧。动作决定哪一帧，真实进度决定沿轨道的水平位置，两者不能互相驱动：换帧不应让总进度前进，网络停滞也不应伪造百分比。

原始四帧脚底分别测得 `594、599、578、574`。显示高度固定，只按 `footY / 627 × 128` 补偿支撑点。轨道每列顶部来自已建立遮罩，角色脚底贴到该列上缘附近，而非固定贴 `canvas.bottom`。这样同时处理了轨道起伏和帧内透明边差异。

不要把这条经验理解为“每帧包围盒底部都必须压到同一条地面”。跳跃和腾空帧本来就应离地；承重姿势按支撑脚标定，腾空高度交给动作或物理模型。不得通过逐帧缩放来贴脚，也不要把脚底校正叠加到已有的跳跃高度上。

检查起点、终点、低进度、小屏和窗口缩放：尾巴不应越过容器裁切边，终点不应挤到徽章外，文字不应被跑动角色挡住。加载停止或遮罩层隐藏后应清理动画计时器。

## 6. 点击开始以后加载，首帧完成以后揭开

用户明确要求入口先显示，点击“开始救援”后才开始游戏加载。当前 `bootstrap.mjs` 先保留首页背景与标题，在原按钮槽位切换为轨道，然后动态引入 Phaser 脚本，再导入游戏模块；避免一进页面就看到游戏加载过程。

当前阶段呈现为：引擎引入后约 5%，引擎资源进度映射到 5%–85%，创建动作与场景时约 88%，引擎第一次 `POST_RENDER` 后到 100% 并隐藏启动层。阶段权重是呈现约定，不代表耗时占比；它们由真实阶段事件触发，不使用定时器持续加百分比。

资源可用的完整链路是：字节到达 → 图片解码 → 纹理可用 → 场景对象与动作缓存建立 → 首次完整绘制。启动轨道显式等待 `track.decode()`；游戏使用引擎加载与纹理创建流程，并在首帧事件后揭开。不要把这一实现描述为“逐张独立记录了所有解码耗时”，当前没有这份遥测。

必须保留的稳定条件：

- 首页、加载轨道和加载角色自身先可见；若角色图片尚未可用，不能展示破图或第二条临时进度线。
- 重复点击只启动一条加载链；失败保留原位置的重试入口，不进入不完整场景。
- 总进度单调上升；阶段文案若已有局部百分比，要移除后再展示总体百分比，避免“资源 100% / 整体 85%”被当成异常。
- 冷缓存、热缓存、慢网络、单资源失败、切后台再回来分别检查；缓存快也需要满足首帧条件，不靠人为拉长动画假装加载。
- 修改代码或资产后，已有浏览器标签可能仍持有旧模块、旧纹理与旧状态；确认实际刷新和资源版本，再判断“改了却没变化”。保留可读版本/状态证据，不能只凭本地文件已保存就汇报效果已显示。

详见 [加载流程](loading.md)。

## 7. 公共反馈由事件驱动，不能每帧覆盖

“没水了”“被蛇咬了”“受到陨石撞击”“掉入坑洞”需要共同的视觉与生命周期。模型发出一次事件，公共反馈组件消费事件；靠近水池的持续提示属于环境提示，不应在每帧更新时覆盖一次性的受伤消息。

当前 `GameFeedback` 使用专用 `toast-v6.png`（**1860×846**）。按宽 420 显示时，左侧圆形图标的真实中心约为容器 `(-150,-5)`，文字区中心约 `(30,-5)`，而不是对称的整图中心。动态文字宽度 266，图标和文字分开绘制。换图片后需重新量槽位，不能假设所有通知壳左右对称。

公共反馈行为：

1. 普通 notice 去重后进入有上限的队列；当前最多 3 条。
2. damage 优先显示，并配合镜头短震、红色闪烁、角色附近心形及 `−1` 上浮。
3. 同图标和同文案 1800 ms 内去重；消息展示约 2100 ms 后淡出。时间是本例参数，复用时依据可读性调整。
4. 展示新消息时先取消旧定时器，并停止旧的淡出 tween。只清定时器而不清 tween，会出现“新消息刚出现就被旧回调隐藏”。
5. 重开与清理同时处理队列、去重状态、计时器、闪光、上浮实体及它们的 tween，避免旧局反馈泄漏到新局。

持续按“倒水”且桶已空，应由输入边沿或模型状态变化发出一次事件，而不是每个渲染帧都调用通知。UI 的短时间去重是第二道保护，不能替代模型的事件语义。死亡结算也要考虑最后一次受击反馈的可见时间，不能立刻被面板遮没。

## 8. 四向键是一张完整图案、四个热区、多份独立输入状态

用户指定的是十字四向键，且要求参考已有游戏，不是四个散开的箭头按钮，也不是连续摇杆。当前复用已存在的十字键图案，在四个方向建立透明热区，图案与输入状态分离；右侧取水、倒水、跳跃键另有图标与按下反馈。

键盘使用 `Set<key>`，触控使用 `Map<pointerId,key>`。行为查询合并两者，触控释放只删对应指针，不能清掉仍按住的键盘键或另一根手指。按住右移的同时取水、跳跃时，应分别记录指针；抬起其中一个不能全部失效。

输入清理覆盖 `pointerup`、`pointerout`、全局释放、移出游戏、窗口失焦与页面隐藏。跳跃等离散动作只在按下边沿触发，取水和倒水的持续动作查询持有状态。按压缩放不应移动热区或引发布局回流。详见 [按钮与虚拟键](buttons.md)。

## 9. 全铺满与安全区是两个问题

`FIT` 可保留整个逻辑画布，但在比例不一致时产生上下或左右空带；用户拒绝了露出的区域。当前使用 Phaser `ENVELOP`：

```text
coverScale = max(viewportWidth / logicalWidth, viewportHeight / logicalHeight)
visibleLogicalWidth = viewportWidth / coverScale
visibleLogicalHeight = viewportHeight / coverScale
```

背景按覆盖方式铺满，接受边缘有裁切；HUD 根据真实可见逻辑宽高缩放、居中，保留边距，不能继续把按钮钉在已经裁掉的逻辑边缘。全屏、窗口缩放和横屏手机需分别检查方向键、暂停、容量、通知和结算按钮。背景使用 cover 不意味着人物、按钮和面板可以被非等比拉伸。

测试时将“素材已裁断”“场景越过视口”“ENVELOP 合理裁切”“透明边造成错觉”分开定位。先验证原图边缘完整，再检查纹理格、容器与视口，最后处理布局；不要直接加遮罩掩盖证据。

## 10. 资产与并行工作的可追溯性

保留生成原始字节，复制到项目而非覆盖源文件。清单记录资产版本、真实尺寸、原图路径、运行时路径、SHA-256、生成回执、参考图、槽位标定与验收状态。历史被拒版本不能改名成“最终版”抹去来源。原图、绑定数据与运行时引用必须能互相追溯。

并行生成独立资产曾用 `Promise.all()`：其中一个请求失败导致外围执行提前结束，其他未等待的任务结果没有可靠收回。对独立任务改用 `Promise.allSettled()`，逐项记录成功/失败及回执，再逐项复制、检查和接入。不能因一个资产失败而把整批标为失败，也不能因多数成功而把缺失项标为完成。依赖操作、源图审核、编辑、接入与验证仍需顺序执行。

“生成成功”“已接入”“规则通过”“浏览器已观察”“用户接受”应分开存储。出图工具的回执只证明产出了文件，哈希只证明字节身份，自动测试只证明覆盖到的规则，三者都不能替代原生画面的美术审阅。

## 实际来源与边界

### 2026-10-15 补充：帧名、随机席位动画与美术验收

Phaser 同一纹理添加命名裁切帧后，后续未指定帧名的 `add.image` 可能读取首个命名帧。用背景纹理额外注册桌沿前景时，返回首页可能把桌沿裁切当整幅背景，再执行 cover 放大。背景始终显式指定 `__BASE`，前景显式指定自己的命名帧；按“首页→其它页→首页”连续往返验证，不能只验首次进入。

多人首页需要干净背景、各角色透明状态图和桌沿遮挡层。每个角色持有独立等待时间与动作队列，随机选择眨眼、转头、举杯，结束后回到较长待机；不共享全局模运算循环。保存原始格框、座位锚点与每角色固定尺度，不能每帧按透明边重新适配大小。四张独立状态图只能证明表情/姿势切换，不应称作四帧顺滑动作或完整战斗动画。

选角上半身与战斗血条头部是不同裁切契约。分开保存 `bustRect` 与 `faceRect`；修改血条头像不能顺带把选角预览改成截断头部。画面中头发、角、耳朵、角色名和血条的遮挡必须实际观察。

统一画风不能只在每张图的提示词中重复“二维”。需要固定同一母版的头身比例、轮廓线宽、色块层级、材质密度和光向。局部改衣裤时锁定原来的身高、头部与姿势；连续重生容易由街机插画漂移成短腿Q版。保留用户否决版本及原因，禁止把“已生成/已接入”写成“用户认可”。
