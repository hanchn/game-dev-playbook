# 加载界面：把“资源可用”变成“画面可见”

用户点击开始后，入口按钮原来的位置切换为加载UI，保留首页主视觉。进度完成才切到游戏。这样既给出反馈，也保持入口位置稳定。是否使用全屏加载由产品流程决定；按钮槽位方案不应额外叠加一个加载弹窗。

## 状态与完成条件

| 状态 | 入口槽位 | 场景 | 可以开始吗 |
|---|---|---|---|
| ready | 开始按钮 | 尚未展示 | 可以触发加载 |
| downloading | 进度轨道和说明 | 隐藏 | 否 |
| decoding | 同一条进度轨道 | 隐藏 | 否 |
| warming | 同一条进度轨道 | 已建立、尚未揭开 | 否 |
| entering | 100%，转场 | 完整场景 | 是 |
| failed | 重试按钮、简短错误 | 隐藏 | 可重试 |

下载成功只意味着字节已到达。对图片等待解码，对引擎等待纹理建立，对场景至少完成首次绘制。首次GPU使用会带来上传开销，因此只用网络请求进度就宣布完成，容易让图标、角色、装饰逐个闪入。

先预加载加载UI自身，包括轨道和加载角色。否则首次点击先出现普通线条，再换成绘制素材，用户会看到两套进度效果。首页不需要常驻一个0%的进度条。

## 真实进度的组合

将阶段分别观测，进度单调上升。例如下载占60%、解码占25%、首次绘制占15%；这是可调整的呈现权重，不是性能结论。每个阶段进度都要来自实际完成数量或字节；缓存命中也要满足解码与渲染条件。无法度量GPU细分工作时显示“准备场景”，直到真实就绪再到100%，不要用固定计时伪造完成。

```text
progress = downloadWeight × downloadedFraction
         + decodeWeight × decodedFraction
         + warmWeight × warmedFraction
```

加载流程要支持失败重试和取消后清理。再次点击不能启动第二条并行加载链。错误时保持原槽位，不把进入游戏按钮留在仍不可玩的场景之上。

## 轨道与角色

轨道只显示一套。移动角色沿轨道端点插值，端点减去角色半宽和透明边，避免最后一帧超出边缘。动画帧只控制划船、飞行或行走动作，进度只控制沿轨道的位置；不要让每帧包围盒变化参与位移计算。

角色与载具使用固定比例和锚点。载具若已烘焙在每帧内，就不能再叠一层静态载具。独立rig则固定底盘，让人物动作在其上播放。小尺寸下检查动作是否还能辨识，不要用原始大图硬塞进轨道。

## 固定出图提示

> 制作[主题]的横向加载轨道空壳，比例[宽:高]，沿用已确认材质和配色。中央留连续可填充航道，左右端点完整，四周透明安全边包含光晕。不要文字、百分比、角色和第二条进度线。角色另出固定画布序列帧，轨道与角色可独立叠放。

## 验收

冷缓存和热缓存分别走一遍：点击立即有反馈，只有一条进度；页面不先揭开场景；100%后首次画面完整；角色不变形、不越界。检查慢网络、单张图片失败、重复点击、切换到后台后返回。记录真实下载、解码和首次绘制耗时，避免把慢渲染误判为慢网络。
