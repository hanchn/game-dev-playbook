# 视觉与运行问题排查

## 街机拆解与移植：已复现问题（2026-10-15）

| 现象 | 本轮处理与边界 |
| --- | --- |
| PCX/SFF导入失败 | 区分SFF v1/v2、RLE边界、LZ5/RLE8/PNG和调色板链接，不接受解码失败的空动作 |
| AIR注释不是UTF-8 | 原包和哈希不变；UTF-8失败后Latin-1保留字节值，数值解析与注释显示分开 |

| 凌空停滞/突然躺倒 | 查CNS物理和状态退出；AIR等待帧不能当普通固定时长。KO必须实际落地并保持倒地 |
| 部分克隆后LFS很慢 | 全仓库LFS遍历触发惰性blob拉取；固定需要的路径后定向smudge并核对哈希 |
| 大批LFS上传时SSH断开 | 开启SSH ServerAliveInterval并重用已传对象；等远程ref更新才报告推送完成 |
| ROM核对成功但不能运行 | 旧SSF2T包缺密钥，23个文件匹配不代表可运行；后续独立MAME完整包已实际运行，勿混淆包身份；SF2CE两项字节证据通过不代表全逻辑/画面已验证 |
| AI整页有很多格但不能用 | 原姿势未对齐、格网/轴心漂移、透明底光晕或重复帧；候选隔离，不计作完成动画 |

每个Epic记录触发条件、来源版本、修复、复现步骤、自动测试和实际引擎观察。测试通过只覆盖实际检查过的层次，不替代美术认可和原作时序验证。

先录下触发场景并定位是素材、帧元数据、渲染状态还是玩法状态的问题。修改后对照同一场景，构建成功不能代替实际观察。下表是可复用检查项，不是已测得的性能结论。

| 症状 | 常见根因 | 如何验证 | 修复方向 |
| --- | --- | --- | --- |
| 左上角出现阴影闪烁 | 阴影在默认坐标可见，精灵已隐藏但阴影仍画，池对象激活顺序不完整 | 检查第一帧和回收瞬间的位置、可见性与关联 ID | 先初始化坐标与状态，最后设可见；精灵与阴影共用生命周期 |
| 透明图出现矩形暗块 | 阴影或滤镜作用于整个透明帧，纹理实际含背景色 | 检查 alpha、关闭滤镜对照、看纹理边界 | 使用轮廓或独立阴影，保留正确透明边；避免矩形阴影替代轮廓 |
| 金币位持续闪烁 | 每帧重建数字 DOM / 精灵，每帧重启动画 | 统计节点创建次数，对比余额未变时的更新 | 缓存显示值，只在数值变化事件更新；脉冲仅在实际变动触发 |
| 重置后高等级仍高亮 | 解锁数据未清、调试存档残留、按目录索引推断 ID | 同时检查默认值、存档版本、解锁集合、生成池 | 明确重置字段并迁移旧数据，调试注入隔离 |
| 角色或载具忽大忽小 | 逐帧按包围盒缩放，站立与坐姿分别适配同一框 | 叠看固定船体 / 头部参照，比较每帧 scale 和 pivot | 使用同一比例、固定基准及根节点；站立应更高而不是整体缩小 |
| 船压扁、出现两艘船 | 非等比缩放补尺寸，旧底船与新整套帧同时可见 | 检查显示宽高比和子层列表 | 保持等比缩放，选定完整帧或分层方案，删除重复船层 |
| 动画抽搐或上下跳 | 每帧主体位置、朝向、构图或尾部差异大 | 逐帧轮廓、根节点与首尾帧对照 | 统一锚点和尺度，重做不连续帧；不要靠整体缩放掩盖 |
| 尾巴裁切、旁边有残片 | 分格越界、邻格泄漏、素材本身越边 | 放大单帧边缘，检查格尺寸与源图 | 使用可靠帧边界与留白，完整主体不靠裁切救场 |
| 雷达压扁、消息越出看板 | 固定高度/max-height覆盖比例，圆形部分与中段一起伸缩 | 检查计算后的宽高与每个切片边界 | 圆形仪表和端盖等比，中段横向伸缩，文字对齐实际槽位 |
| PNG 视窗露出下一行素材 | 源矩形包含邻格或 SVG 目标比例引入空白 | 对照源矩形与实际手机截图 | 先修源矩形，再明确视窗比例与 overflow；不拉伸角色 |
| 按住方向撞墙看不到反弹 | 输入在下一帧抵消向内速度，或边界使用了错误的缩放坐标 | 原生键盘持续撞三条边，观察位移与速度 | 短暂锁定反弹轴输入，按真实可视边界及船体尺寸碰撞 |
| 倒着游或倒着跑 | 素材默认朝向与 flip 规则相反 | 用单个目标分别向左右移动 | 在元数据声明默认朝向，统一渲染翻转规则 |
| 水母不停放大缩小 | 用 scale 模拟推进，或每帧尺寸归一化 | 暂停移动后观察帧和 scale | 保持整体大小，使用局部形变帧表现收缩 |
| 图鉴切卡像直接替换 | 动画期间提前换层、隐藏出场卡、仅换索引 | 慢速查看出场、重排、入栈时序 | 先让原卡移出，再调整顺序并回到卡堆，保持可见层差 |
| 加载结束后素材逐个出现 | 网络完成当作渲染完成，图片尚未解码，纹理首次上传 | 冷启动录首帧；核对解码、纹理、关键图标 readiness | 加载门控涵盖解码和纹理准备，准备完成后统一显现 |
| 弹窗背景也播放角色动作 | 世界与 UI 共用动作触发，结算未冻结世界 | 暂停时检查模型时间、Tween 和世界动作 | 分离世界 / UI 时间与动作实例，进入覆盖界面冻结世界 |
| 回后台后瞬移或回合结束 | 恢复时累计巨大 delta | 记录恢复首帧 delta | 暂停模型，恢复清理累计时间，限制单步时长 |
| 热更后对象重复或输入失效 | 旧实例、监听器、定时器未销毁 | 对照完整刷新；统计场景与监听器数量 | 明确销毁生命周期，防止多次绑定；用冷启动复验 |
| 运行越来越慢 | 池未回收、离屏更新、每帧分配、滤镜开销 | 先记录帧时间、实例数、分配与 GPU / CPU 负载 | 针对测出的瓶颈优化，不先盲目降画质 |
| 素材多后卡顿和内存高 | 大透明 PNG 与超大图集，解码纹理远大于文件体积 | 统计解码尺寸、驻留纹理及同屏使用 | 合理分图集与按需驻留，控制分辨率，分离图鉴与场景资源 |

## 性能测量顺序

1. 固定设备、视口和场景，保留冷启动与稳定运行两种记录。
2. 记录帧时间分布而不只看平均 FPS，区分加载峰值和持续卡顿。
3. 统计可见与隐藏对象、池数量、纹理尺寸、DOM 更新、滤镜和分配。
4. 判断 CPU、GPU、资源上传或垃圾回收哪一项主要受限。
5. 一次改变一个主要因素，在相同场景复测。

没有实测数据时，写“待验证”，不要声称提升某个百分比。只限制鱼数量并不代表预算合格；装饰、阴影、浮物与飞鸟也会消耗渲染和更新资源。

## 透明纹理的成本

一个普通 RGBA 解码纹理的基础存储约为 `宽 × 高 × 4 字节`，与压缩 PNG 文件大小不同。实际显存还取决于格式、mipmap、上传副本和驱动行为。透明留白同样占用纹理空间，因此不能用“小文件”推断“小纹理”。

裁剪留白时必须保留动作安全边距，并让帧元数据继续使用共同尺度与锚点。图集压得过紧可能出现采样邻格；保留 padding 并验证缩放状态下的边缘。

## 修复后验收

至少复验冷启动、开始游戏、首次生成、抓捕、出画回收、图鉴打开与切卡、结算动作、重开一局。涉及存档时再验默认数据和重置。保持日志、截图与实际观察相符：通过测试、通过构建、看过动画是三件不同的事。
