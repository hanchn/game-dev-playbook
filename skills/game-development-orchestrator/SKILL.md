# 主动完成游戏开发

用户希望提出游戏目标后，Codex 主动处理完整方案和实施。先读当前项目指令、需求记录、已有源码与实际画面；继承当前游戏的玩法、风格、平台和授权，不把示例题材或引擎当默认。单点修复沿用已有方案，避免重做整款游戏。

## 形成可制作的方案

在当前项目维护 game-plan.json 与简明设计说明，补齐相互关联的信息，并随实现更新：

- 游戏方式与玩法：操作、目标、核心循环、成功/失败、奖励、重试、进度和难度；用玩家实际经历的一个回合说明规则。区分已有规则、合理假设和待确认选择。
- 架构：沿用适合的已有源码和引擎，明确规则、渲染、输入、UI、存档、数据与资产接口、事件、状态、时间管理；先验证最小可玩回合。
- 场景：入口、教学、首个挑战、进阶和结算的路线、镜头、尺度、碰撞/导航、交互、遭遇与素材分层。用区域目的规划地图，不只填装饰。
- 角色：身份、比例、视角、部件归属、近远肢体、手型/抓握、动作和交互；逐个做代表样本与真实动作后扩展。
- 完整 UI：主动使用可用的 game-ui-suite，做玩法相关页面流、HUD、操作反馈、弹窗、按钮状态、响应式布局、套图清单、独立动态文字和数字、实现与QA。
- 交付与质量：保存源码/素材来源及版本、实际导出、游戏接入、测试入口、失败与同姿势复测；性能预算随实测修订。

缺少信息先从已有项目和用户描述推断，记录必要假设。只有改变主要目标且无法推断的选择才问用户，同时继续独立工作。普通可逆制作不设置额外审批。

## 调用生产能力

需要生成、编辑或批量处理时读 [工具入口](references/tools.md)。生成计划不能替代用户要求的制作。

- infinite-map-generation：可复现分块、有限区域通行检查和真正游戏接入分开。
- keyframe-generation：当前角色的FK编辑与关键姿势；插值不等于解剖修复或自动锁脚。
- sprite-animation-production：以我们的真人、外星人和动物核对真实图集、比例、逐帧与运行播放。
- sprite-art-qa：逐关节、近远侧、深浅背景、弯曲极限、完整动作和实际尺寸。内侧腿须有回收、抬起、落脚；模板相位和边界通过不替代实际观察。
- game-ui-suite：生成/实现独立素材和状态后组装页面；背景概念图不能当可用按钮或HUD。

先检查已有本地资源项目（例如 game-asset-studio）的实物源码，再适配并记录具体文件/commit/hash。收藏目录、计划和截图不能冒充已复用实现。只读取任务相关内容。

## 验收与进度

先实际操作最小回合，验证目标可达、输入反馈、失败/成功和重试，再扩内容。QA覆盖启动/解码/首帧、操作、动作切换、暂停恢复、保存恢复、屏幕适配、生命周期和性能；按玩法增删，不机械添加无关场景。

planned、generated-candidate、technical-passed、visual-reviewed、game-integrated、user-accepted 分开。没看的记 not-reviewed，不用测试数量提升美术状态。已知缺陷继续修并保留证据；切换任务记录未完成工作，不用新角色遮住旧问题。

舰队仅在当前授权允许时分派文件和接口明确的独立任务。当前项目角色制作仍按顺序，独立生成器/工具可并行；无授权时自己完成。
